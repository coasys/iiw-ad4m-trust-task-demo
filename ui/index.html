Every button shows the @coasys/ad4m calls it made and what came back. Passwords, passphrases and tokens stay on the server.

Someone sends a signed ToIP trust task (acl/grant/0.2, "give Carol the role member") to an AD4M space. The people in the space vote through a flow. When the flow ends, AD4M makes a receipt of how they decided. The space sends back a signed answer with that receipt in it, and the sender checks it.

You run all of it here, on your own computer, against your own AD4M node. Go through the steps in order. The same steps exist as commands in demo.mjs and requester.mjs; this page calls the same functions.

1 Get the executor

The AD4M executor is the program that runs your node. It holds your keys, stores your data as signed links, and runs flows. It is one file. The page needs to know where it is.

2 Start the node

Your node is the executor running with its own data folder (.node/). The page starts it the way start-node.sh does. The first start creates the folder and a random admin credential: whoever has that file controls the node. This page's server reads it and never shows it.

Multi-user mode

A yes needs two voters. With multi-user off you are alone on this node, so you can only say no, unless a second node joins your space (step 5).

3 The node's agent, and people on it

  
An AD4M agent is a key pair and a did:key. Everything the agent writes is signed with that key. A new node has no agent yet: you create one and protect it with a passphrase. After every restart the agent is locked, and you unlock it with the same passphrase.

  

  

    
People on this node (multi-user mode)

    
In multi-user mode one node holds several people, each with their own DID and keys. Each has a login (email and password). The page makes a random throwaway password for each and keeps it in .demo/people.json, so it can log them in later. Logging in gives a token for that person.

    

      
      
    

    

  

  







  
4 Connect this page to your agent

  
An app never gets your keys or the admin credential. It asks the node for a capability: the right to act as your agent. The node answers with a one-time 6-digit code that only you can see. Here the node writes the code to its log. You read it there and type it into the app. Only then does the app get a token. That way a web page can ask, but only the person at the node can say yes.

  
In the ADAM launcher the code shows up in a window. A bare executor started by this page approves the request on its own and prints the code to its log (that is what AD4M_LOG_SECRETS=1 does).

5 Make a space

  
A space (AD4M calls it a perspective) is a graph of signed links. The trust tasks, the flow and the votes all go in it. A local space stays on this node. A neighbourhood is a shared space: other nodes join it by its URL, and AD4M syncs the links between them.

  

  

    

      
Local space

      
Only this node. Needs no network. In multi-user mode a person on this node owns it and the node's agent is in it too, so the two of them can vote.

6 The trust task and the flow it becomes

  
On the left is a trust task as the requester sends it: plain JSON with an Ed25519 proof (eddsa-jcs-2022). On the right is what AD4M makes of it: a class that stores the request, and a flow, a small state machine. Votes move a run of the flow from state to state. Two votes accept the request. One vote rejects it.

7 Vote

  
Each received task has its own run of the flow. Every person in the space votes with their own key; AD4M signs each vote as a link. Nobody sets the state directly: each node works it out from the signed votes it holds. The highlighted box is the state this node sees now.

  
 

  

  







  
8 The receipt, the answer, and the requester's check

  
When a run ends, AD4M makes a flow receipt: the signed votes, the final state and the exact request the group decided on. Its address is the SHA-256 of its content, so nobody can change it unnoticed. The space wraps it into a signed trust-task answer. The requester checks the answer against the request it sent.

What this does not show: AD4M does not make or check the eddsa-jcs-2022 proofs itself; this demo holds the space's trust-task key in its own code. Accepting records the grant in the space; no AD4M permission changes. The requester checks the receipt's hash and that it names its exact request; the AD4M signatures inside the receipt are checked by the members' nodes (verifyFlowReceipt).
