A ToIP trust task, decided by an AD4M flow

A runnable demo for builders: Coasys, for IIW 43 / AIW Interop Day, November 2026.

Someone asks your group to give Carol the role member. They send the ask as a ToIP trust task: a small JSON document of type acl/grant/0.2, signed with their did:key. Your group keeps its work in an AD4M space. The space holds a flow, a small state machine with voting rules. Two members vote. When the flow ends, AD4M makes a receipt of how they decided, and the space answers the requester with a signed trust-task response that carries the receipt. The requester checks the answer on their own.

You run all of it: one AD4M node on your laptop and two JavaScript files with Node. demo.mjs is the AD4M side, one command per step, written with plain @coasys/ad4m SDK calls. requester.mjs is the other party.

1. The trust task

This is what node requester.mjs request writes to out/request.json (DIDs shortened):

{
  "id": "urn:uuid:971c3202-…",
  "type": "https://trusttasks.org/spec/acl/grant/0.2",
  "issuer": "did:key:z6MkeZd6…",          ← the requester
  "recipient": "did:key:z6MksgYv…",       ← the space's trust-task key
  "issuedAt": "2026-11-01T23:13:40.512Z",
  "expiresAt": "2026-11-02T00:13:40.512Z",
  "payload": {
    "entry": {
      "subject": "did:key:z6MkhaXg…",     ← Carol
      "role": "member",
      "act": { "scope": "contexts", "contexts": ["iiw-demo/notes"] },
      "keys": { "scope": "none" },
      "capabilities": { "scope": "ceiling" }
    },
    "reason": "IIW 43 demo: let Carol join the notes space"
  },
  "proof": { "type": "DataIntegrityProof", "cryptosuite": "eddsa-jcs-2022", … }
}

The signing and checking use ToIP's own TypeScript libraries, @openvtc/trust-tasks and @openvtc/trust-tasks-proof.

2. The flow it becomes

In the space the task becomes social DNA: a class for the stored request, and a flow that runs on it. Both are links in the space, so every member's node has the same rules.

The flow in demo.mjs (trustTaskFlow()):

const flow = new SHACLFlow('TrustTaskDecision', 'iiw://');   // iiw://TrustTaskDecisionFlow
flow.inputTypes = ['IiwTrustTaskRequest'];
flow.consensusRule = { n: 1 };
flow.addState({ name:'Received', value:0 });
flow.addState({ name:'Accepted', value:1, consensusRule:{ n:2 } });
flow.addState({ name:'Rejected', value:2, consensusRule:{ n:1 } });
flow.addTransition({ actionName:'Accept', fromState:'Received', toState:'Accepted', actions:[] });
flow.addTransition({ actionName:'Reject', fromState:'Received', toState:'Rejected', actions:[] });

the signed JSON, as receivedIiwTrustTaskRequest.raw, byte for byte

receiver checks: proof, recipient, schema, freshness, duplicatesrun before anything is stored; then state Received
the maintainer grants itAccept: Received → Accepted, 2 votes
the maintainer refuses itReject: Received → Rejected, 1 vote
answer acl/grant/0.2#responseAccepted + flow receipt in payload.ext["org.coasys.ad4m"]
answer trust-task-error, permissionDeniedRejected + flow receipt in payload.details["org.coasys.ad4m"]

Each vote is a link signed by the voter's AD4M agent. Minting and checking a receipt work the state out from those votes each time (status shows the state the node last worked out). n:2 counts any two distinct voters in the space; it does not check roles. The flow receipt is content-addressed: its address is the SHA-256 of its body, and it carries the signed votes and the exact request the group decided on. node demo.mjs show prints this table; show --links prints the links AD4M stores.

3. Get a node running

You need Linux or macOS, Node.js 22 or newer with npm, and the AD4M executor v0.13.1.

Before the release is out. Until v0.13.1 is published, its download links return 404. This demo was tested with the staging build v0.13.1-staging.6: its executor from the AD4M releases page and @coasys/ad4m 0.13.1-staging.6. Use the 0.13.1-staging.6 file names below until then.
chmod +x ad4m-cli-executor-linux-0.13.1-x64
export AD4M_EXECUTOR="$PWD/ad4m-cli-executor-linux-0.13.1-x64"
./start-node.sh init      # creates .node/: the node's data and its admin credential
./start-node.sh run       # in its own terminal; Ctrl-C stops it
npm ci                    # in a second terminal

4. Local mode: one node

Two people on one node. Bob is the node's own agent. Alice is a second user on the same node (AD4M's multi-user mode) with her own DID. Each signs their own votes.

node demo.mjs agent --as bob          # creates the node's agent; asks for a passphrase twice
node demo.mjs users add alice         # multi-user mode on; alice gets her own DID
node demo.mjs show                    # the trust task next to the flow
node demo.mjs space                   # alice makes the space and installs the flow; bob is in it too

node requester.mjs request            # the requester signs a task to the space
node demo.mjs receive out/request.json
node demo.mjs vote accept --as alice --why "Carol should join"
node demo.mjs vote accept --as bob --why "Agreed"
node demo.mjs respond                 # mint the receipt, check it, sign the answer
node requester.mjs verify             # the requester's own checks

The passphrase is not shown while you type and is not written anywhere. After a node restart the agent is locked; run node demo.mjs agent again. agent --remember keeps the passphrase in .demo/agent-passphrase (readable only by you) if you prefer. users add makes a random throwaway password for each person and keeps it in .demo/people.json, so --as alice can log her in.

Try the other paths: on a new request, vote reject --as bob ends the flow at Rejected and respond signs a trust-task-error that still carries the receipt. Change the request after signing and receive refuses it with proofInvalid; nothing is stored. npm test runs all of these with assertions.

5. Shared mode: two nodes

Alice and bob each run their own node. Alice shares the space as a neighbourhood; bob joins it by URL; AD4M syncs the space's links, votes included, between the nodes. Each person needs their own copy of the demo folder and a running node.

Alice's machine

node demo.mjs agent --as alice
node demo.mjs space
node demo.mjs share
neighbourhood neighbourhood://Qm…

Bob's machine

node demo.mjs agent --as bob
node demo.mjs join neighbourhood://Qm…
flow iiw://TrustTaskDecisionFlow synced in
node requester.mjs request
node demo.mjs receive out/request.json
node demo.mjs vote accept --as alice
node demo.mjs status            # until the task shows
node demo.mjs vote accept --as bob
node demo.mjs respond
node requester.mjs verify
# copy alice's out/response-….json here as answer.json
node demo.mjs check-receipt answer.json

If bob's vote has not reached alice's node yet, respond says the flow is not finished; run it again a few seconds later. The requester only talks to alice's node, which holds the space's trust-task key.

Which link language

A neighbourhood needs a link language to move its links. share takes one of the two the release knows:

More people on one node

node demo.mjs users add carol adds another person to a node. Two users on one node share a space through a neighbourhood as well: after share, run node demo.mjs join neighbourhood://… --as carol on the same node, then vote accept --as carol.

6. Offline

Downloading the executor and npm ci need the network. After that, local mode needs none: the space, the flow, the votes and the receipt all live on your node. How we checked: we could not cut a test machine off the network, so we pointed the node's HTTP(S) proxy and its Holochain bootstrap, relay and proxy at a dead local address. A fresh node, and the same node after a restart, ran every local step and npm test; strace saw no connection to the internet, only discovery on the local network. The node logs that it cannot fetch some of AD4M's Languages; the local steps do not use them.

Offline, a space on one node holds two people: one user on the node and the node's own agent. Two users on one node can share a space only through a neighbourhood, and making a neighbourhood needs the network: offline, share says so and stops. Shared mode needs the network throughout.

7. What it does not show

  • AD4M making or checking eddsa-jcs-2022 proofs. demo.mjs does that with ToIP's library and its own throwaway key.
  • A permission change. Accepting the acl/grant records it in the space; no AD4M permission changes.
  • The requester re-checking AD4M's signatures inside the receipt. AD4M's verifyFlowReceipt does that on the members' nodes; the requester checks the hash and that the receipt names its exact request.
  • A trust-task transport. Files stand in for HTTPS, DIDComm or TSP.
